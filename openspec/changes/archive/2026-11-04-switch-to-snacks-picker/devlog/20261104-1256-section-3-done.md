# Section 3 done: command palette

<!-- Section: 3 · Tasks: 3.1–3.3 · Base: e532279 -->

`<leader>fp` palette (`multi` = keymaps `modes = { "n" }` + commands, title "Command Palette"),
`<leader>fk` keymaps, `<leader>fc` commands, in `lua/plugins/snacks.lua`.

Findings (both contradicted design.md's "Snacks picker facts"):
- **`multi` can't dispatch to a string confirm.** `config/init.lua` calls `confirms[item.source_id](...)`,
  and `commands`' confirm is `"cmd"` → "attempt to call a string value" (reproduced headless). The palette
  has its own `palette_confirm`, which routes on `item.cmd` (command) or else replays the mapping
  (`picker:norm` → close → `nvim_input(item.item.lhs)`, same as snacks' keymaps confirm).
- **snacks' `cmd` action doesn't run the command**; it types it on the cmdline. I asked the user, and
  they chose: run user/plugin commands whose `nargs` is `0`/`?`/`*`; type everything else (built-ins
  have no nargs info) on the cmdline via `Snacks.picker.actions.cmd`. This applies to `<leader>fp`
  and `<leader>fc` (`run_command`). The picker spec (palette + keymap/command requirement text),
  design decision 3 and AGENTS.md were updated to say so.

Headless verification (scratch script in `%TEMP%\opencode`, not committed):
- no-arg user command runs from the palette;
- an `nargs=1` command is prefilled (not run) from both `fc` and `fp`;
- the `[T]erminal [T]oggle` entry closes the palette and calls `nvim_input(" tt")`;
- palette keymap items are all mode `n`.
- `:Lazy` opens no window headless (no UI), so it couldn't be the test; it's `nargs="?"`, so it takes
  the run path. Its real UI is checked in §4.
- Gotcha: `nvim_input` keys aren't processed while blocked in `vim.wait`, and a feedkeys-driven test
  hung in cmdline mode. Stubbing `actions.cmd`/`nvim_input` was the reliable way to test the routing.

Self-review vs spec: nothing else found. Snacks is still not loaded at startup.
